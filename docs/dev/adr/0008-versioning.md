## 背景

利用者から，次のように決めるよう指示を受けた．

- セマンティック バージョニングを使う
- Windows 版が出るまでは v0.0.1 から始め，修正や機能を入れて配るたびに v0.0.2 のように PATCH だけを上げる．MAJOR と MINOR は変えない
- macOS 版と Windows 版は別々に管理することになるが，機能に差があるのはおかしい．一方で，両方そろわないと出せないとすると，片方だけの安全上の修正が遅れる

## 決めたこと

### 番号の意味

| 部分 | 意味 | 共通か |
|---|---|---|
| MAJOR | 設定のファイルや辞書の形など，入れ替えに手間がかかる変更 | 両方で共通 |
| MINOR | 機能の水準．同じ MINOR なら，macOS 版と Windows 版は同じ機能を持つ | 両方で共通 |
| PATCH | 不具合と安全上の修正，見た目の調整 | バージョンごとに別 |

- 「v0.3.x」と言えば，どちらのバージョンでも同じ機能がそろっていることを表す．機能の差は MINOR を見れば分かる
- 新しい機能は，両方のバージョンに入れ終わってから MINOR を上げて出す．片方だけに先に入れた機能は，次の MINOR までは既定で無効にする
- 不具合と安全上の修正は，片方のバージョンだけで PATCH を上げてすぐに出してよい．もう片方を待たない
- core(両方が使う部分)を直したときは，両方の PATCH を上げる

### Windows 版が出るまで

- macOS 版だけを 0.0.x で出す．入れて配るたびに PATCH を 1 つ上げる(0.0.1 → 0.0.2)
- Windows 版を初めて出すときに，両方を 0.1.0 にそろえる．ここから上の決まりで進める

### 置き場所と名前

- バージョンは `apps/macos/project.yml` の `MARKETING_VERSION`(Windows 版はそのプロジェクトの同じ役の値)だけに書く
- ビルド番号(`CURRENT_PROJECT_VERSION`)はバージョンごとに 1 ずつ上げる整数．同じバージョンを作り直したときも上げる
- Git のタグは `macos/v0.0.2`・`windows/v0.1.0` のようにバージョンごとに分ける
- 上げるのは `tools/release/bump_patch.sh macos` で行う(PATCH とビルド番号を 1 つずつ上げる)
- 設定の画面と README には「v0.0.2 (macOS)」のように，バージョンと OS を並べて出す

## 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 両方を常に同じ番号にする | 片方だけの安全上の修正を出すときに，変えていないバージョンまで上げることになる．逆に待たせると修正が遅れる |
| バージョンごとにまったく別の番号にする | 機能の差が番号から分からず，「どのバージョンでこの機能が使えるか」を表で管理しなければならない |
