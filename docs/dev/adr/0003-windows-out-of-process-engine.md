# 0003 Windows では変換を別のプロセスで行う

- 状態: 採用
- 日付: 2026-10-25

## 背景

Windows の TSF のテキストサービスは DLL で，入力先のすべてのアプリのプロセスに読み込まれる．辞書とニューラル変換のモデルはそれぞれ数百 MB になる．権限の高いアプリや AppContainer のアプリにも読み込まれる．

## 判断

- TSF の DLL は Rust で書き，キーの受け渡しと入力欄への反映だけを行う
- 変換は，ユーザーのログオン中に 1 つだけ動く `s90-engine-host`(Swift)で行う
- 両者は名前付きパイプで通信する．形式は `protocol/` に定義し，両方の言語のコードを生成する
- 候補ウィンドウは別のプロセスで描く

azooKey-Windows も同じ分け方をしている．

## 検討したほかの案

| 案 | 採らなかった理由 |
|---|---|
| DLL の中で core とエンジンを動かす | アプリごとに辞書とモデルを読み込むことになり，メモリと起動時間を食う．エンジンの不具合が入力先のアプリを落とす |
| DLL も Swift で書く | COM の実装と panic の扱いの面で，Rust の windows クレートの方が実績がある |

## 結果

入力先のアプリに読み込まれるコードが小さくなり，落ちたときの影響もエンジンのプロセスに閉じる．
通信の分だけ遅くなるので，1 キーあたりの往復の時間を計測して CI で見張る．通信の安全については `docs/dev/SECURITY-MODEL.md` の「Windows のプロセス間通信」に従う．
