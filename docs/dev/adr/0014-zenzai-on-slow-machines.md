# 0014 Zenzai が遅い環境では，打鍵が止まる前の表示に Zenzai を使わず，打鍵の合間に追いかけて求める

- 状態: 採用
- 日付: 2026-10-27
- 関係する要件: R-01

## 背景

ADR 0006 は，Zenzai の推論を打鍵ごとに同期で行うことにした．Apple Silicon では 1 キーの処理が 50ms 以内に収まったためである．
Windows では llama.cpp を CPU で動かす(macOS は Metal を使う)．i7-12700F で測ると，長い文を打ち進めるほど 1 キーの時間が延び，
40 字を超えると打鍵のたびに 35〜80ms(最大 170ms)かかった．人の速さ(90ms 間隔)で 84 打鍵の文を打つと，31 打鍵が 50ms を超えた．
DLL は 50ms を超えた返事を後から反映するので文字は消えないが，表示が打鍵に遅れてついてくる．

llama.cpp の AVX2 版・Vulkan(GPU)版，推論のスレッド数(2・4・6・8)，1 回の変換で推論する回数の上限(10・5・3)も試したが，どれも 1 キーの時間はほとんど変わらなかった．
遅いのは，打鍵ごとに文全体を Zenzai にかけ直すことそのものだった．

## 判断

- Zenzai を使った変換の時間の移動平均を測り(`AzooKeyConverterEngine.recordZenzaiCost`)，予算(`DefaultSettings.zenzaiTypingBudget`，25ms)を超える環境だけ，打鍵が止まる前の表示(ライブ変換)を Zenzai なしで求める．
  予算は R-01 の 50ms から，Zenzai 以外の処理と DLL との往復の分を除いたもの．速い環境(Apple Silicon)では今までと変わらない
- 打鍵が止まったとき(settle)・Space・変換中の操作は，これまでどおり Zenzai を使う
- 打鍵の合間に，Zenzai の変換と分岐図の候補を追いかけて求めておく(Windows は DLL の wake，macOS は settle を待つ Task)．人の打鍵の間隔は 1 打鍵分の Zenzai の差分の変換より長いので，ほとんどは次のキーが来る前に終わる
- azooKey は前の読みからの差分で変換するので，打っている文・その続きでない読み(分岐図の文節の残り・Backspace で戻った読み)・Zenzai なしの入力中の表示で，セッションを分ける．同じセッションで交互に求めると，差分が使えず毎回一から変換して遅くなる
- 表示は追いかけた結果ですぐには変えない(打鍵のたびに字が変わって見えるのを避ける)．止まったときに Zenzai の結果を出す

## 検討したほかの案

| 案 | 採らなかった理由 |
|---|---|
| Windows では Zenzai を使わない | 変換の正しさが落ちる(ADR 0006 の評価で 23/24 → 14/24) |
| 推論を Vulkan(GPU)で行う | この PC では速くならず，GPU や Vulkan の無い環境で起動できなくなるおそれがある |
| 1 回の変換で推論する回数を減らす | 1 キーの時間がほとんど変わらなかった |
| 推論をエンジンの別のスレッドで行い，結果を後から表示に反映する | azooKey の変換器はスレッドセーフでなく，変換器を 2 つ持つと辞書と学習の状態を分けて持つことになる．合間に追いかける方法で十分に速くなった |

## 結果

長い文(84 打鍵・90ms 間隔)で，1 キーの中央値 35ms → 8ms，50ms を超えた打鍵 31 → 2，打ってすぐの Space 190ms → 120ms，止まってからの Space 90ms → 30ms(Windows，i7-12700F，Release)．
`LatencyProbeTests` は，アプリと同じく打鍵の合間に追いかけて求める(Zenzai が遅い環境だけ)．

代わりに，遅い環境では打鍵が止まるまでの表示が Zenzai を使わない変換になり，止まったときに Zenzai の結果に変わることがある．
