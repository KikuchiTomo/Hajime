# 0017 同梱のモデルと辞書は，前回と同じファイルなら起動のたびにハッシュを求め直さない

- 状態: 採用
- 日付: 2026-11-13
- 関係する要件: R-01，R-25

## 背景

起動のたびに，アプリに同梱した Zenzai モデル 2 つ，jinen モデル 2 つ，かな漢字変換の辞書(約 8000 ファイル)の SHA-256 を求め，リポジトリに書いた値と比べている(`StartupResources`)．
合わせて 500MB ほどを読むため，確かめ終えるまでエンジンを作れず，起動から最初の変換までの大半をこの確認が占める．
Windows ではサインインのたびに `hajime-engine-host` が起動するので，毎回この時間とディスクの読み込みがかかる．

ハッシュを確かめる目的は，取得したファイルが壊れていないこと，取得元で差し替えられていないことを確かめることである(取得の時点では `tools/models/fetch_zenzai.sh` と `tools/dictionary/fetch_dictionary.sh` も確かめる)．
同梱のファイルはアプリのインストール先(macOS は `Hajime.app` の中，Windows は `C:\Program Files\Hajime`)にあり，そこを書き換えられる人は実行ファイルも書き換えられる．
一度確かめたファイルが変わっていないことが分かれば，読み直して確かめても防げるものは増えない．

## 判断

- 確かめ終えたファイルについて，大きさ・更新日時・ファイル ID(Windows はボリュームのシリアル番号とファイルのインデックス，macOS は st_dev と inode)をまとめた値を記録する
- 次の起動で，ファイルごとのこれらの値と，アプリのバージョン，照らし合わせる SHA-256，ファイルの場所がすべて前回と同じなら，ハッシュを求めずに確かめた結果を使う．どれか 1 つでも違えば，今までどおり読んで確かめ，合えば記録を書き直す
- 辞書は一覧(`SHA256SUMS`，約 700KB)を毎回読んで SHA-256 を確かめ，一覧にあるファイルの値だけを記録と比べる(一覧の中身を記録に頼らない)．
  Windows はファイルを 1 つずつ開くと 8000 ファイルで 0.3 秒ほどかかるので，ディレクトリごとに一度だけ読んで値を得る(`GetFileInformationByHandleEx` の `FileIdBothDirectoryInfo`)
- 記録するのは確かめて合ったものだけで，合わなかったものや無かったものは記録しない(次の起動でもう一度確かめる)
- 記録は利用者ごとの場所に，本人だけが読み書きできる権限で置く．中身は確かめた結果(上の値をまとめた SHA-256・照らし合わせた SHA-256・場所・アプリのバージョン)だけで，入力した文字は含まない
  - macOS: `~/Library/Application Support/<サポートのディレクトリ>/` の下(0600)
  - Windows: `%LOCALAPPDATA%\haji.men\IME\` の下(ユーザーのプロファイルの ACL を受け継ぐ)
  - ファイル名と大きさの上限は `DefaultSettings`(`verificationRecordFileName`，`maximumVerificationRecordBytes`)
- 記録が無い，読めない，形が違う，大きさの上限を超える，形式の番号が違うときは記録を使わず，すべて確かめ直す
- アプリのバージョンは，macOS は `CFBundleShortVersionString` と `CFBundleVersion`，Windows は `hajime-engine-host.exe` 自身の大きさ・更新日時・ファイル ID とする(Windows のエンジンはアプリのバージョンを持たないため．入れ直せば実行ファイルが置き換わり，値が変わる)

## 検討したほかの案

| 案 | 採らなかった理由 |
|---|---|
| 確認をやめる | 取得の途中で壊れたファイルや，ディスクの上で壊れたファイルを読み込むおそれが残る．初回と変わったときは確かめたい |
| 確認を裏で行い，終わるまで Zenzai と辞書なしで変換する | 起動してすぐの変換の質が下がり，確かめ終えたところで候補の出方が変わる．ディスクの読み込みと CPU の時間も減らない |
| 大きさと更新日時だけを比べる | ファイルを置き換えて更新日時を戻す操作で，同じ値にできる．ファイル ID も比べれば，置き換えたファイルは別のファイルとして確かめ直す |
| 記録に HMAC などの署名を付ける | 記録を書き換えられる人(利用者本人と管理者)は，鍵も同梱のファイルも書き換えられる．守れるものが増えない |
| 確かめた結果をインストーラーが書く | インストールのあとにファイルが壊れたことに気付けない．macOS と Windows で別の仕組みが要る |

## 結果

2 回目からの起動では，同梱のファイルの確認が，辞書の一覧を読むこととファイルの属性を調べることだけになる．
`hajime-playground --startup`(エンジン側と同じ順で，確認・エンジン・warmUp・最初の変換)で測ると，Windows(i7-12700F，Release，ファイルは OS のキャッシュに載った状態)で
確認は 0.69 秒から 0.07 秒に，最初の変換までは 0.84 秒から 0.21 秒になった(どれも 8 回の中央値)．初めての起動と入れ直したあとの起動は今までと同じ時間がかかる．

代わりに，同じファイル ID のまま中身だけを書き換え，大きさと更新日時を元に戻したファイルは確かめ直さない．
これはインストール先に書き込める人(管理者)にしかできず，その人は実行ファイルも書き換えられるので，受け入れる．
